## Global constraints
1. Every LLM call goes through `lib/llm.ts`, which only talks to `MUBIT_BASE_URL`. No provider URLs anywhere else (unit test greps for them).
2. The Juror system prompt is a constant in `prompts/juror-v1.md`, loaded at build time; never templated. Brand, taste memory and the image go in the user message.
3. Juror output: JSON `{design, usability, creativity, content}` integers 1-10 and `note` (<= 140 chars); `overall` (mean, 1 decimal) is computed by the app, not the model. Whole response <= 400 chars. Validated with zod; invalid output becomes an error card, never a crash.
4. No key = MOCK mode: deterministic fixtures, a visible `MOCK` chip, and the same code paths otherwise. Setting `MUBIT_API_KEY` + `MODEL` switches to `MUBIT` with no code change.
5. Generated HTML is untrusted. Defence in depth: (a) sanitiser removes `<script>`, `<iframe>`, `<object>`, `<embed>`, `<link>`, `<meta http-equiv=refresh>`, `on*=` attributes, `javascript:` URLs, CSS `@import`, and any `url(...)` or SVG `href`/`xlink:href` that is not a `data:` URI; (b) a CSP meta tag is injected first in `<head>`: `default-src 'none'; style-src 'unsafe-inline'; img-src data:; font-src data:`; (c) display in `<iframe sandbox="" srcdoc>` (no scripts, no same-origin); (d) the screenshot browser runs with JavaScript disabled and aborts every request that is not `data:` or `about:`. Unit tests feed payloads using each vector and assert nothing survives; a screenshot test asserts zero network requests.
6. All brand values come from `src/styles/tokens.css`, generated by `npm run tokens` from Kimberley's `brand/colour/tokens.md` and `brand/type/tokens.md` (her single handoff). Empty rows fall back to the provisional DESIGN.md values, each marked `/* provisional */`. Nobody edits tokens.css by hand. UK English, no emojis, no em dashes in UI copy.

## Surfaces
1. **The Wall `/`** (default view, ready on first load): header with Pika wordmark, the current brand kit, mode chip (MOCK/MUBIT), batch controls (`Generate batch`, `Reset`). A grid of 12 cards. Each card: sandboxed live render of the section, rank badge, the four Juror scores + overall + note, and actions `Move to top` and `Score it yourself`, plus drag-to-reorder (pointer events). Right rail: **Taste memory** (list of corrections with reasons, newest first) and a one-line explainer of what happens on correction.
2. **Brand `/brand`**: choose a preset (Pika, provisional tokens; Mubit, colours from mubit.ai labelled "from mubit.ai, unconfirmed") or fill a short form: name, three colours, display font, body font, tone (one line). Saves to `data/state/brand.json`.
3. **Scorecard `/scorecard`** (DEMO-READY requires real data: >= 8 held-out sites, each row with an awwwards.com source link, the four jury scores, a measured big-model score, and a small-model score (measured or recorded in Try models); plus the correction-proof table. Until then the page shows the empty state and the build is "MOCK-complete", not "demo-ready"): table of held-out sites: real Awwwards jury scores (with source link), Juror scores, error, and for each model run: median latency, tokens, cost per 100 critiques; a method box explaining how numbers are computed. Empty state when no results yet: says "No scorecard run yet" and shows the method and the command. Never invented numbers.

## Pipeline
1. **Generate** (`POST /api/batch`): 12 generator calls in parallel (concurrency 4) through `lib/llm.ts`; each asks for ONE hero section as self-contained HTML (inline CSS + inline SVG only, <= 6 KB, no scripts, no external assets except Google Fonts link stripped in favour of a font stack) for the brand kit, with a different layout seed (12 seeds: split, centred, editorial grid, oversized type, asymmetric, image-led with SVG shapes, brutalist, minimal, bento, marquee-style static, stacked, magazine). Results stream to the client as each finishes (SSE).
2. **Render + screenshot** (`lib/shot.ts`): sanitise, render in headless chromium with JavaScript disabled at 1280x720, JPEG q70 -> data URL.
3. **Judge** (`lib/juror.ts`): one Juror call per card: system = constant prompt; user = brand kit summary + up to 6 most recent taste-memory examples (each: the art director's preference and reason, plus the corrected scores) + the image. Parse with zod. Card gets `data-scored=true`, `data-family=<layout seed family>`, and `data-taste-applied=true` when >= 1 taste example was included.
4. **Rank**: by `overall`, ties by `design`. Rank 1 badge has `data-testid=rank-1`.
5. **Correct** (`POST /api/correction`): drag a card to a new position (pointer events; drop on a slot; keyboard alternative: focus a card, Alt+Up/Down), `Move to top`, or `Score it yourself` all open a small sheet with an optional reason (`data-testid=reason`) and Save (`data-testid=save-correction`). Saves `{cardId, batchId, juror scores, director rank/scores, reason, timestamp}` to `data/state/taste.json`, re-ranks the current Wall with the director's choice pinned, and shows it in Taste memory. If Mubit exposes a correction/rating API (HUMAN-NEEDED question), `lib/corrections.ts` also forwards it; until then it logs "Mubit correction API not configured" in the server log, not the UI.
6. **Next batch** uses taste memory automatically (step 3). Controlled check: the layout seed family promoted by the correction must rank higher in the next batch than its baseline rank for the same brand without taste (MOCK: deterministic; MUBIT: shown as a before/after comparison on the same 12 seeds). The journey checks the visible result: the promoted family's card must appear earlier in the Wall's rendered order (DOM order and on-screen position agree) and its visible rank badge text must show a smaller number than in the no-taste baseline batch.
7. **Mock mode**: generator returns 12 templated HTML sections built from the brand kit (real HTML, varied layouts). Juror mock scores each layout from fixed per-seed baselines plus a deterministic adjustment: layouts that share the seed family of a promoted card gain +1.5 overall, demoted families lose 1.0. Labelled MOCK everywhere; the README states the mock logic.

## Scorecard
- `data/scorecard/sites.json` (human-filled; HUMAN-NEEDED): `[{name, awwwardsUrl, jury: {design, usability, creativity, content}, screenshot: "data/scorecard/shots/<file>.jpg", takenBy, takenAt}]`. Screenshots taken by us; no site code stored.
- `npm run scorecard`: runs the Juror on each site with `MODEL` (big) and, if Mubit lets apps call adapters, `MUBIT_ADAPTER_MODEL` (small); records scores, latency (ms, wall clock per call), and token usage from `response.usage`. Writes `data/scorecard/results.json`. Mean absolute error vs jury per criterion and overall.
- Small model when apps cannot call adapters: the team runs the same held-out inputs in the console's Try models (side by side) and records the small model's JSON replies in `data/scorecard/trymodels.json` `{site, reply, recordedBy, recordedAt}`; the scorecard shows them in a column labelled "Mubit adapter (recorded in Try models)". Cost and speed for the small model: measured if apps can call the adapter; otherwise the page states "small-model cost and speed: not measurable from our app; Mubit's console comparison shown instead" and the proof pack lists the cost/speed comparison as an unmet demo-ready criterion. Never estimated.
- `npm run check:demo-ready` (strict validator, exit 1 on any gap): every site in `sites.json` has an awwwards.com URL, all four jury scores (numbers 1-10), `screenshot` file present, `takenBy`/`takenAt`; `results.json` has, per site, a big-model reply with model id, timestamp and usage, and a small-model reply with adapter version id or `trymodels.json` provenance (`recordedBy`, `recordedAt`); `correction-proof.json` has before/after version ids, 6 replies each, timestamps, and passes the directional rule. JR-3D also requires the page to show the validator's PASS stamp (`data-testid=demo-ready-pass`), rendered only when the validator's output file says PASS for the current data hash.
- Prices: `data/pricing.json` `{ "<model id>": {"inPer1M": number, "outPer1M": number, "source": "<provider pricing URL>", "checkedAt": "YYYY-MM-DD"} }`, filled from the provider's public pricing page. Cost per 100 critiques = 100 x mean(input_tokens x inPer1M + output_tokens x outPer1M) / 1e6. If usage or price is missing for a model, that cell shows "unavailable" with the reason; never estimated.

## How a correction becomes a model update (both routes defined)
- Wording rule: the UI and pitch say "model update" only when the correction proof passes; otherwise "the Juror applies your correction on the next call".
- Instant: the correction enters taste memory and the NEXT Juror call's user message (this is visible within seconds).
- Model update, route A (if Mubit exposes a correction/rating API): `lib/corrections.ts` sends it; the demo shows the console entry.
- Model update, route B (no correction API): every Juror call after a correction carries it, so the adapter version trained on those calls learns that taste.
- **Correction proof (DEMO-READY gate for either route):** a fixed comparison set of 6 held-out sections plus one fixed correction. Record in `data/proof/correction-proof.json`: adapter version id BEFORE the correction (or "no adapter yet"), adapter version id trained AFTER calls containing the correction, and both versions' Juror replies on the 6 sections (from Try models or the app if callable), with timestamps from the console. **Frozen evaluation:** both adapter versions are evaluated on byte-identical messages: the constant system prompt, the same 6 images, the same brand line, NO taste-memory or correction text in either, same settings (temperature 0, same max tokens). The evaluation messages are stored in `data/proof/frozen-eval.json` with a hash; the validator rejects a proof whose replies were not produced from that hash. So any difference comes from the model update, not from the prompt. **Directional rule:** the proof passes only if, on the fixed set, the after-version moves toward the correction: the section matching the corrected preference gains rank or overall score relative to the before-version, on at least 4 of the 6 comparisons, computed by `npm run check:demo-ready` (not by eye). If it fails or no route is verified, the demo claims taste memory only ("the Juror applies your correction on the next call") and never says "model update". The scorecard page shows the before/after table and the computed result. If no adapter version trained after the correction exists by Sun 09:00 (daily training cap), the demo claims only the instant taste-memory change and says on screen "the model update lands on Mubit's next training run"; this is listed as unmet in the proof pack.

## Assumptions (strike any)
